# craftagent —— 精密制造工艺数据 -> 异常归因

一次只做一件事：**把机床的工况数据和三坐标的抽检结果对到同一条时间轴上，
自动说出"哪台机在漂、什么时候开始漂、是谁先动的、下一步该做什么"。**

不用 GPU，不用 pandas，不用联网。整个包只用 Python 标准库，
因为工厂那台电脑上少一个依赖就少一个装不上的理由。

## 跑起来

    cd D:\Users\china\Desktop\项目_开发\craftagent
    python -m craftagent synth                 # 造一份合成数据（里面埋好了真值）
    python -m craftagent analyse --spec 8.5    # 对齐 + 变点 + 归因，写出 out/report.md
    python -m craftagent verify                # 拿埋好的真值验收方法本身
    python -m craftagent ask "为什么圆度超差了"
    python -m craftagent ask "哪台机在漂" --machine M01
    python -m craftagent grade --auto-mask     # 方法对师傅判断的恢复率

换成真数据只要三个文件：`machine_log.csv`（工况，一分钟一行）、
`cmm_report.csv`（三坐标抽检）、`profile.json`（这个工序的物理常识和老师傅经验）。

## 四个文件的分工

    profile.json   工艺档案：信号分三类，加已知症候和老师傅经验。唯一需要行业知识的地方。
    align.py       时间轴对齐。格式各家一套、时间还对不齐，真正难的就是这一步。
    changepoint.py 变点检测：最小二乘二分分割 + 抗离群显著性检验。
    attribute.py   归因：块中位数差分互相关，定"谁先动"；读数量给"去查哪个上游旋钮"。
    annotation.py  六要素标注表（情境/线索/判断/动作/边界/结果），append-only。
    grader.py      恢复率评分器：机器算的 vs 师傅说的，五问逐条证伪。

报告和回答一律只给**相关性排序**并写明这四个字。因果要拿工艺常识和设备手册核对，
系统不替人下这个结论。


## 上游接一段：G 代码 -> 内核 -> 门 -> 虚拟机床 -> 归因

原来这条链的入口是"工况日志 + 三坐标抽检"。现在在它前面接上一段，
**归因器一行不改**就能吃新表——如果为了接新数据源必须改归因器，
那说明前面的对齐层本来就是假的。

    G 代码 --解析/规划(C 内核 + Python 对拍)--> 安全门 --> 虚拟机床 --> 两张同形的表
                                                     |                       |
                                                     |                       +-> 原来的链路原样跑
                                                     +-> 事前拦截，给出行号

    python -m craftagent cnc analyse out/demo_bad.nc   # 一条程序跑完整链
    python -m craftagent cnc gate   out/demo_bad.nc    # 只跑门，报放行/拒绝和理由
    python -m craftagent cnc verify                    # 真值验收 + C/Python 对拍
    python -m craftagent cnc bench                     # 门的两个数 + 每条规则的消融对照
    python -m unittest tests.test_collide              # 撞刀那四条（9 条）
    python -m craftagent cnc cam-verify                # 图纸->参数->G代码->门 的四个数

### 上游那一层：图纸 -> 参数 -> G 代码

上面整条链从"已经有一条 G 代码"开始。可是那条程序是谁写的？
如果答案是"大模型写的"，那么这个项目最该被质疑的地方就在这里：
**模型算算术题会算错，而且错得看不出来。**

让它"根据材料、直径、齿数算主轴转速"，它会给你一个像模像样的 3827 rpm。
那个数可能对，也可能是把 vc=80 代进了 vc=180 的式子——两者都是四位有效数字，
都写在正确的量纲里，**从结果上看不出来**。而车间里的后果不一样：轻则表面烧伤，
重则断刀。

所以这一层的分工是：

    模型说"这是什么材料、什么工序、什么刀具"   -> 分类，它可以做
    手册把分类变成 S 和 F                      -> 查表，它不该做

    feeds.py    切削参数手册：五组材料 x 三种刀具材料 x 四道工序，每条有出处公式
    drawing.py  DXF 解析：LWPOLYLINE/ARC/CIRCLE，层深写在图层名里
    cam.py      轮廓 + 层深 -> 分刀 -> G 代码，并**自检再返回**

三条公式就写在这个仓里，不藏在代码里（这个仓的习惯）：

    n  = 1000 * vc / (pi * D)
    fn = z * fz
    vf = n * z * fz
    Pc = ap * ae * vf * kc / (60e6)          [kW]

最后那条功率式是这张表**唯一能自我反驳**的地方：查出来的 F 若让机床超功率，
那"手册说可行"就是假的。它会真的把进给夹下来，并把"是谁夹的"记进 `clamped`。

#### 为什么每齿进给不是按直径线性缩放的

第一版写成 `fz = 比例 * D`（比例 0.020），于是 D10 钢粗铣得到 `fz = 0.20 mm`、
`vf = 1621 mm/min`。那个数落在门的进给上限之内、功率只有 0.52 kW，
**所有自查都说"合规"**——而 0.20 mm/齿对一把 D10 硬质合金刀是断刀的进给。

错的地方在假设：fz 随直径涨，但涨得比线性慢得多（刃口钝圆半径近似是个常数，
大刀具靠刚性多切一点，不是按比例多切）。刀具厂给的是分档表，就按分档查。
`FZ_STEPS` 里的档位越界时取端部值而不是外推——外推一个从没被验证过的区间，
是让"看起来合理"替掉"有人验过"。

#### 开链拼环：真实图纸里没有 LWPOLYLINE

大多数图纸导出的轮廓不是 LWPOLYLINE，而是一堆 LINE/ARC 首尾相接。
不拼环就等于"这张图纸没有可切的轮廓"——而那通常是假的。

拼环这件事有一个必须做出的决定，写在这里而不是藏在代码里：

    分叉怎么办？三条边共用一个端点时，走哪条？

这台机器做的是"按最小转角继续"（车间里人眼会做的那个选择），
并且**把每一次这样的猜测都数出来**（`Contour.assumed_junctions`
与报告里的 `junctions` 列表）。理由：一个悄悄挑了一条边的拼接器，
会生出一条看起来完全正常的轮廓，而它是错的。

不猜（遇到分叉就放弃）在这里更糟：真实图纸会因为一个无关的标注端点
就整张拼不出来，而"拼不出来"和"这里分叉了"是两条不同的信息。

几条都写在代码里、也都有测试盯着的规则：

  * **不跨图层拼**。不同图层是不同的层深，跨层拼接会悄悄把半条轮廓的
    深度改掉，而改完之后它看起来完全正常。
  * **深度不明就不拼**。拼出一条深度是错的轮廓，比拼不出来更糟。
  * **拼不上的要说缺口多大**。"拼不上"和"这里差 72.11 mm"是两条不同的
    信息：前者让人以为图纸坏了，后者能让人直接去图纸里找那 72 mm。
  * **段没有 ENDSEC 结尾时也收下**。真实图纸会被截断（U 盘拷一半、
    邮件附件断掉）。截断的文件里 ENTITIES 仍可读，而"一个段都没闭合
    所以整张图是空的"是一句比事实更严重的谎。

#### 写这段时被自己抓到的三个错，都留在这里

  * **文件里有两个 `stitch()`**。第一版写在中间，第二版追加在文件末尾，
    Python 取后定义的——于是"改成新版本"之后，跑的仍然是坏的那份，
    而单步追踪明明是对的。教训：改完之后要 grep 一下 `def 名字` 的**个数**，
    不然"我改好了"这句话本身就该被怀疑。

  * **LWPOLYLINE 的顶点配对是"按出现顺序交替"，不是"20 配最近的 10"**。
    我按后者写，三个顶点的型腔被读成两个坏点，报"闭合轮廓少于 3 个点"。
    报错是对的，原因说的是假的——那种错最难查，因为它看起来像图纸有问题。

  * **一条测试绿着描述了一个已经不存在的行为**。`test_unsupported_entities_
    are_reported_not_skipped` 原本断言"LINE 进 unsupported"，那是拼环之前
    的事实。拼环做出来之后 LINE 不再是"读不懂"而是"攒起来用"，
    于是这条测试变成了一边通过、一边说着假话。改完之后它盯的是真的
    读不懂那一类：块引用（INSERT）。

#### 图纸里读不懂的东西必须说出来

`drawing.py` 自己写 DXF 解析，不用 ezdxf。两个理由，第二个更要紧：

  * 本机 `import numpy` 直接 MemoryError（traceback 打出来看的），而 ezdxf 依赖它。
  * 这个仓从第一天起只用标准库。一个"必须先 pip install 才能看图纸"的工具，
    在车间里等于不能用。

`unsupported` 与 `unknown_depth` 不是装饰。**图层名里读不出层深时，它不猜 0**：
猜 0 的后果很具体——那条轮廓会被当成"在表面上划一刀"，门放行，件是废的，
而所有报表都是绿的。开链（单独一条 LINE/ARC）也没有被假装闭合成环，
它被报出来，因为"这条线切不出件"是信息，"图纸读完了"不是。

#### 闭环：被门拒绝之后怎么办

这是这条链唯一闭环的地方，也是它值得存在的理由：

    查表定参数 -> 生成 -> 门 -> 若拒绝，把保守系数乘小 -> 再来

方向由**拒绝理由**决定，不是由"哪个参数看起来更安全"决定：门的拒绝理由是圆度，
圆度由跟随误差主导，而跟随误差随进给线性涨（见 `plant.py` 的闭式解），
所以降的是进给。降转速不改变进给，它改的是切口速度和每齿厚度，那是另一件事。

而且只对**降进给能解决**的理由重试（`quality_predict` / `accel_limit`）。
撞刀、超行程、缺主轴是几何与程序结构问题：撞刀降进给不会让刀绕开压板，
把它们也拿去重试，只会白跑八轮之后报"试过了都不行"，把真正的原因埋掉。

    python -m craftagent cnc feeds                          # 印出整本手册
    python -m craftagent cnc feeds --material N --diameter 6 --flutes 3
    python -m craftagent cnc cam data/demo_plate.dxf --stock=-10,-10,70,50,0,28
    python -m craftagent cnc cam-verify                     # 这条链的四个数

实测（`cnc cam-verify`，45 组材料 x 工序 x 刀具）：

    一次性命中      38 / 45 放行（84.4%）      不追回退时手册本身的可信度
    闭环回退        7 / 7 被拒的最终放行        轮数分布 {2:3, 3:1, 4:2, 6:1}
    生成器自检      15 条程序，问题 0 个       每一刀都在毛坯内、都到得了图要求的深度
    读不懂的说明    开链 True；无深度 True     不是"图纸干净"，是"脏的被点名了"
    开链拼环        从 4 条 LINE 拼出 1 个闭合轮廓、未采用实体 0 个

两个数必须分开报：只报回退后的 100%，一个"什么都慢慢来"的策略也能拿满分，
而它把材料性能全浪费了；只报一次性命中率，闭环的价值看不见。

被拒绝的那些主要是铝和钛在高转速下：门的 `quality_predict` 说圆度会到 22.79 um，
规格是 8.5 um。这正是这条链想做的事——**不是让模型生成一个看起来合理的数，
而是让一个数在被执行之前先被物理否掉一次。**

一个真实的例子（铝 D6 三刃，型腔 + 外轮廓 + 沉孔，问一次）：

    尝试 k=1.000  拒绝：quality_predict   (F 1527, 预测圆度 22.79 um)
    尝试 k=0.741  拒绝：quality_predict
    尝试 k=0.549  拒绝：quality_predict
    尝试 k=0.406  放行                     (F  621)

    python -m unittest tests.test_cam            # 这一层（17 条）

### 为什么有一个 C 内核

规划表是纯算术，Python 跑一遍 60 微秒，离线分析完全够用。C 内核存在的
唯一理由是**对拍**：两份独立实现逐段同意，才说明规划结果是对的。
同一份代码跑两遍永远同意，那测的是确定性，不是正确性。

    bench/build_cncrt.py    编内核（找不到 gcc 就明说不跑，不假装成功）
    cncrt/src/plan.c        前瞻 + 插补，只做这两件事
    bench/pair.py           同一条程序两边各算一遍，逐段比 v_entry/v_peak/v_exit/t_s

当前：三组形状（含圆弧、极短段、长行程）全部一致，max|dv| = 3.3e-5 mm/s
（就是 4 位小数的量化误差），C 单次 tick 0.04~0.10 微秒。

### 安全门：两个数必须一起报

    legal    64 / 64 放行，误拒 0
    planted 284 / 284 拦住，且 244 条都由**指定的那条规则**拦住
    关掉任一条规则 -> 那一类故障的拦截数塌到 0 / 40

只报拦截率，一个"全部拒绝"的门能拿满分而它什么也没做。所以放行率必须一起报。
消融对照是唯一让拦截率有意义的部分：关掉某条规则之后还拦得住，那是碰巧拦住的，
报出来的数就不属于那条规则。

未由指定规则拦下的那 40 条是 `accel_limit` 那一组：关掉 accel_limit 之后，
它们仍被 `quality_predict` 拦住（0.05 mm 的极短段在 F6000 下预测圆度超差）。
两条规则报的是同一个物理，所以"关掉 accel 仍拦住 40/40"不是消融失败，
而是这次消融在说：那个物理在这个数据上有两个出口。bench 现在会把"是谁接住的"
一起打出来，否则这一行会被读成"accel_limit 这条规则没用"。

### 撞刀那四条：料之外的东西

前六条规则问的是"这条指令本身越界没有"，全部关于**被加工的那块料**。
可是车间里废掉机床的，往往不是料：是压板、是台面、是刀柄。

    table_crash         刀尖落到台面以下
    clamp_crash         刀尖进了压板
    holder_crash        刀柄进了料（伸出量不够，也就是"刀具长度这一栏填的是假的"）
    rapid_into_stock    快速移动从料里横着穿过去

它们是**几何**规则，所以单立一个 `collide.py`，需要毛坯、压板、刀具三样东西，
而不是并入 gate_cnc 的前六条。混在一起以后，想只跑前六条就得假装没有毛坯——
那正是最容易骗自己的一步。

三条取舍写在文件里，都是实测出来的：

  * **高度场而不是体素**。三轴机的刀轴竖直，材料只能从上面被削短，
    所以"每个 (x,y) 一个 z"是精确的，不是近似。五轴就不是了，
    所以这个文件不声称支持五轴。

  * **快速移动只在横移时判**。每个程序结尾都有 `G0 Z` 直着抬出工件，
    把那条判成"穿过材料"会让门拒绝世界上每一份程序。抬刀不切东西，
    因为刀已经在那个柱子里了。

  * **圆弧真的要沿弧采样**。只取两端点或取弦会漏掉鼓出来的那一段：
    弦在弧的内侧，撞到压板的那一点恰好可能不在弦上。

#### 三条在写这四条规则时被自己抓到的错，都留在这里

  * **一条死规则**。我写了"刀柄撞压板"，写完发现它永远轮不到：
    刀柄与刀尖同轴，且 `刀柄底面 = 刀尖 + 伸出量` 恒在刀尖之上，
    所以刀柄进压板时刀尖必然更在里面。删掉了。留着它让人以为门管了四件事，
    而实际只管三件。真要区分"刀柄蹭压板侧面而刀尖没进"，得把刀柄半径算进
    x-y，那是真几何，这个仓没实现，所以不声称有。

  * **故障先被别的规则拦了**。撞刀故障的坐标一开始落在机床行程之外，
    于是 `axis_limit` 先拦了，那四条一次也没被考过——而报表上写着"全部拦住"。
    同一件事换个方向又出现一遍：故障程序没带 `M3 S`，于是被 `spindle` 先拦。
    现在每条故障都带 `M3 S8000`，并且 bench 会记下"关掉这条规则后是谁接住的"。

  * **两个默认值互相矛盾**。机床 Z 上限原来是 10 mm，而压板顶面在 12 mm、
    安全 Z 在 14 mm：这台机床按默认参数**退不出夹具**，任何一次正确的抬刀
    都会被 `axis_limit` 拒绝。矛盾的方向正好是"看起来门很严"。
    改成 100 mm（够退刀，也给主轴鼻子留位置），并写了一条测试盯着它。

还有一次是别人抓到我：`collide.py` 里第一条合法程序我写了 `G2 X.. Y.. I0 J5`
而终点不在那个圆上，解析器带着行号拒绝了它。这次是它先抓到我的。

### 质量预测门：拦的是"每个参数都合规、结果仍报废"

前五条规则检查**指令是否越界**。第六条检查的是**越界之前就已经做不到**：
进给在额定内、行程也在内，但拐角处的跟随误差让圆度超差。
这是真实车间里最常见的报废原因，也是事后抽检唯一能发现的那一类。把它放进门里，
就是把事后抽检变成事前拦截。

物理只有一条假设，写在这里：每根轴对指令位置是一阶滞后 `x' = (x_cmd - x)/tau`。
对 `x = a t^2/2` 的解析解是 `e(t) = a tau^2 (t/tau - 1 + exp(-t/tau))`。
两个极限都是错的用法：加速期间 `e ~ a·tau·t` 无界增长，匀速之后收敛到 `a/kv^2`。
**拐角误差要用加速期那一支**——拿稳态值代替代价是算小 24 倍，
而算小的方向恰好是"看起来一切良好"的方向。

这条式子可以被独立反驳：tests/test_cnc.py 里用数值积分跑同一台伺服，与闭式解比到 2%。

### 两条回答路径，分别报数

    gate_on=True   事前拦截：门在切削前挡住，报出行号
    gate_off      事后归因：门不拦，机床真的切了，用变点 + 效应量找回来

只跑前者，一个全部拒绝的门能拿满分，事后归因从来没被考到；
只跑后者，门就完全不在验收范围内。两者的分母不同，**不合并成一个百分数**。

归因用**效应量**（变点前后中位数差 / 稳健尺度），不是相关大小：
故障是进给阶跃，拿相关去评判阶跃是在用错尺子——连续量必然赢，
而那个"赢"与模型对不对无关，只与信号形状有关。所以两条排序都报，
`by_corr` 和 `by_effect` 各回答一个不同的问题。

另外一条不能让步的：**质量不能是任何一个通道的仿射变换**。
写成 `q = q_base + k*follow_err` 时，跟随误差就是质量的精确线性像，
它在归因里必然排第一——那不是发现了原因，是把我自己写的那行公式念了一遍。
这就是循环论证，也正是这个仓从头到尾在防的那件事。

## 信号必须分三类，否则报告会自相矛盾

    knob     可调设定参数（进给、转速、修整量）—— 报告给"改成多少"
    symptom  量出来的症状（电流、振动）—— 它不可调，报告给"症状要降到多少，质量才回来"
    readout  环境读数量（温度、湿度）—— 它动了说明上游旋钮动了，去查上游

一边说"砂轮钝了"、一边说"把振动调低 2.5 mm/s"，就是没分这三类。

## 验收（这是这个项目最值钱的部分）

`synth` 造数据时把真值写死：M01 主轴电流与振动同刻起升，**质量滞后 40 分钟**超差，
旁边一台 M02 完全健康。跑完看方法能不能恢复出来，以及会不会把健康机报成故障。

    python -m craftagent verify

当前：5 项全过（漂移机台检出、健康机台不误报、变点位置误差 12 分钟、
驱动信号领先量在容差内、驱动信号进入候选）。结果写在 out/verify.json。

没有真值的项目，方法对不对全靠嘴，所以这一步不能省。


## 我不做实时闭环，我做闭环之前那一步

实时闭环控制需要的是一条数据回路（在线测、在线调），那是另一类系统的事。
这里做的是它前面那一层：**各家各式的数据对不齐、时间轴不一致，归因无从谈起。**
这一层的产品是两个东西——**最小场景单元的归因**，和**把师傅的隐性判断变成可复现的标注**。

### 一、最小场景单元：给线索，不给配方

师傅现场看一次异常，拆成六要素记一条（append-only，改主意就追加一条 supersedes）：

    情境 situation   哪台机、哪一批、哪一班、在干什么（换批/换砂轮/夜班/停机后重启）
    线索 clues       他当场看到听到摸到什么，从哪几个读数上看出来的
    判断 judgement   blamed_channel + syndrome + 窗口 + 置信度 + 凭什么   ← 可验证字段
    动作 action      做了什么，按顺序，带参数
    边界 boundary    invalid_when + 预期的领先分钟                      ← 可验证字段
    结果 result      动作之后质量回来了没有

读数量（温度/湿度/冷却液）排到前面时，报告给的不是"把温度调走"，而是
**"去查它上游哪个旋钮"**——`attribute.UPSTREAM` 那张表就是这条线索的来源，
并会标出其中哪些旋钮本批数据里根本没有记录（那就是到现场第一批要采的参数）。

    python -m craftagent template --out annotations/template.json
    python -m craftagent stamp --machine M01 --say "声音发闷，电流和振动一起抬，温度慢半拍" --master 王师傅
    python -m craftagent analyse --warmup-skip 120     # 师傅说"刚开机头两小时不算"

### 二、标注方法：不是收知识，是验方法

    python -m craftagent grade --auto-mask

拿机器算出来的东西，去核对师傅说的话，五问每一问都能被证伪：

    1 通道名次      师傅指的通道，机器排进前 N 了吗
    2 变点窗口      师傅说的"从这时起不对"，机器检出的变点落在他给的窗口里吗
    3 领先量误差    师傅预期的领先量，机器测出来差多少
    4 症候一致      师傅对上的症候，机器匹配到的是同一个吗
    5 边界遵守      把师傅声明"不算"的段（预热/换批）整段丢掉重算，结论会不会变

第 5 问是这套东西的核心：**师傅的话不是被告，是尺子，但尺子本身也要被检验。**
判据用"结论有没有变"，不用"领先量差多少"——田间没有领先量的真值，
师傅说的那个数本身就是被测对象，拿它当尺子会把自己量歪。
所以领先量的两个数都留在报告里，**不许挑好看的那个**。

分数低的地方先怀疑方法，再怀疑师傅。这就是"跟岗观察 + 联合标注"的数字化：
师傅指认异常，机器同步记录，然后验证归因方法能不能恢复师傅的判断。
一个师傅的经验够用了，要的是这套方法可复现。
